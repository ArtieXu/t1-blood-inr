实测（本次装了 torchkbnufft 1.5.2 直接构造验证）：


#### 先厘清：grid_size 不是 FOV，也不是重建矩阵 **[实测]**

这条管线里有三个都叫「grid」的东西，只有一个跟 FOV 有关：

| 名字 | 是什么 | 谁定的 |
|---|---|---|
| **FOV** | 真实视野，`FOV = 1/Δk` | **采集序列**定的，任何重建参数都改不了 |
| **`im_size` = N = 216** | 重建矩阵。voxel = FOV/216 | `gassp1_data.mat` 里的 `N`，传给 `SpiralNUFFT` 的第 4 个位置参数 |
| **`grid_size` = 432** | Kaiser-Bessel gridding **内部的过采样缓冲区**，算完就丢 | `--kb_grid_size`；不传则 torchkbnufft 取 `2 × im_size` |

torchkbnufft 自己的 docstring 就是这么写的：
> `grid_size; Optional: Size of grid to use for interpolation, **typically 1.25 to 2 times im_size**.`
> `n_shift; Optional: Size for fftshift, usually im_size // 2.`

为什么要过采样：gridding NUFFT 的流程是 **去 apodization → 补零到过采样网格 → FFT → 用一个 6×6 的 Kaiser-Bessel 小核插值到非笛卡尔采样点**。过采样倍率压制的是插值核旁瓣带来的混叠。1.25–2 是标准区间（Beatty 2005：1.25× 配稍宽的核 ≈ 2× 的精度，内存省一半），所以 216→324 是 1.5×，216→432 是 2.0×。

**实测证明它跟几何无关**（`probes/nufft.py`）：把点源放在 (70,140)，forward→adjoint 走一圈——

```
 grid_size   峰值位置    峰值幅度
       216   (70, 140)   0.071052
       324   (70, 140)   0.071052
       432   (70, 140)   0.071052
       648   (70, 140)   0.071052
```

**同一个像素、同一个幅度。** 位置、缩放、FOV、voxel 尺寸全都不变，变的只有插值残差。

#### 那 324 和 432 的差别到底有多大 **[实测]**

拿**精确 NUDFT**（无网格化近似）当金标准，前向投影同一个体模：

| grid_size | 倍率 | vs 精确 NUDFT | gridded 张量 (50帧×28线圈) |
|---:|---:|---:|---:|
| 216 | 1.00× | 1.87e-3 | 0.49 GiB |
| 270 | 1.25× | 1.13e-3 | 0.76 GiB |
| **324** | 1.50× | **7.81e-4** | **1.09 GiB** |
| **432**（默认） | 2.00× | **5.37e-4** | **1.95 GiB** |
| 648 | 3.00× | 4.64e-4 | 4.38 GiB |

两点值得注意：

- **432 比 324 更准**（5.4e-4 vs 7.8e-4），不是更差。超过 2× 之后精度触底（648 只到 4.6e-4）——因为那时误差由核宽 `numpoints=6` 决定，不再由网格决定。
- **324 与 432 彼此的差异是 8.7e-4**，而所有 image gate 阈值在 **5e-2 ~ 1.5e-1**，P2 记录的 data NRMSE 是 2.31e-2。**差了一到两个数量级。**

#### 所以后果修正为：

1. ~~**可比性：这是 AGENTS.md 禁止的「换了变量还叫单变量比较」**~~ —— **我上一版把这条说重了。** 算子差异 8.7e-4，比任何被测指标低一到两个数量级，**不可能翻转任何科学结论**。而且 `run_info.json` 会记录 `kb_grid_size`（`train_inr_unsup_spiral.py:434`），可追溯。这是一个**文档/复现口径的不一致**，不是科学风险。严格 ablation 里仍然应该钉死它——理由是「matched 就该是 matched」，且成本为零，而不是因为 1e-3 会影响结果。
2. **显存：这条站得住。** 432 的 gridded 张量比 324 大 0.86 GiB；实测走完前向+反向，28 线圈下相差约 **1.7 GiB**。在 11.94 GiB 的卡上这是真金白银。
3. **另外**：`train_inr_unsup_spiral.py:69` 的 help 写着 "parity-validated value is 324"，但 `HANDOVER.md`（那份 operator parity 交接文档）**通篇没有记录 324 这个选择的来源或依据**，只提到 parity 用的是 torchkbnufft **1.4.0**（现在环境是 1.5.2），且「exact complex-image parity is not achieved，Python 与 MATLAB 差 10.04%」。**在 10% 的既有失配面前，讨论 8.7e-4 的算子差异没有意义。**

**[实测] 用真实形状在 CPU 上跑 `SpiralNUFFT` 前向+反向，按线圈数外推到 28 线圈：**

**传 324 省约 1.7 GiB。** 我的 `smoke.sh` 第一版也漏了这个参数，已修（现在默认 `KB_GRID=324`）。

## 二、会影响结果解释的问题（不阻塞运行）

### P4 · 32 步不是 1600 步的前缀 **[源码]**

`model.py:31` `epochs_per_level = max(1, epochs // n_levels)`
`model.py:61` `StepLR(step_size=max(1, epochs // 2))`

都从 `--epochs` 派生。32 步时 LR 在第 16 步减半，1600 步时在第 800 步。
**每步耗时和显存峰值可以外推，loss 轨迹不能。**

### P5 · `TI_START_MS` 在默认时间坐标下被数学消掉 **[实测]**

`--time_coords ti_span` 做 min-max 归一化：`t = (TI - min)/(max - min) = n/(F-1)`，与 TI 起点无关。
且我用你存档的参考曲线重拟合验证过：三参数 IR 模型的 **T1 对常数 TI 平移严格不变**（TI=50 和 TI=63 都得到 1871.843 ms），只有 Mz/M0 差 1.5%。
规则该留（出处 + 反转效率解释），但**它不是一个能改变训练数值的实验变量**。

顺带核对：trainer 的时间坐标 `eps + (1-2eps)*t`（eps = 1/(2×50) = 0.01）与 P2 notebook line 675 的 `0.01 + 0.98*t` **完全一致**。这一处没问题。

### P6 · seed 相同不等于初始化相同 **[源码]**

脚本自带 `--shared_init_path`，且 `shared_init_action` 的默认值就叫 `'seed_only'` —— 这个设计本身说明作者知道 tcnn 的初始化未必跟随 `torch.manual_seed`。
**任何 Gate C 的 matched parity 必须传 `--shared_init_path`，只固定 seed 不够。** 冒烟测试不受影响。

### P7 · 输出目录相对 CWD **[源码]**

`train_inr_unsup_spiral.py:411` `log_path = './log/{tag}_{timestamp}'`，没有 `--out_dir`。
带时间戳所以不覆盖旧结果，但落点取决于从哪启动。`smoke.sh` 用先 `cd` 解决，没改脚本（它在 manifest 里有 SHA-256）。

## 三、查过之后**不是**问题的（省得你担心）

| 怀疑项 | 结论 |
|---|---|
| **WSL 只有 7.3 GiB 系统内存会不会不够** | **[实测/估算] 大概率不是瓶颈。** h5py 读进来的 `k_data` (28,50,3315) complex128 = 74 MB，smap 10 MB，`recon_final.mat` 两个数组各 18.7 MB。主机侧没有 GB 级占用。真正的压力全在显存。 |
| **`LRLoss` 核范数会不会出 NaN** | **[实测] 不会。** 50×46656 复数矩阵的 nuclear norm，CPU forward 0.22 s / backward 0.02 s；在奇异值大量重复（秩 1）的退化情况下梯度依然全部有限。注意 `--lr_weight` 默认 **0.0002 ≠ 0**，所以这个 SVD 每步都在跑——是笔耗时，不是风险。 |
| **`torch.quantile` 有 2²⁴ 元素上限** | **[实测] 不触发。** `robust_scale` 输入是 (50,1,216,216) = 2,332,800 < 16,777,216。 |
| **总显存够不够 12 GB** | **[估算] 够，但要传 324。** 逐项：NUFFT 前向+反向 ≈2.7 GiB(324) / 4.4 GiB(432)；INR 参数 + Adam ≈0.66 GiB；hash 编码输出 0.14 GiB；常驻 kdata/smap/wi/pos ≈0.15 GiB。合计约 **4 GiB(324) / 5.7 GiB(432)**，对 11.94 GiB 有余量。但 CPU RSS ≠ CUDA 分配，且 tcnn 在 torch 缓存分配器之外单独开 arena（`train_inr_unsup_spiral.py:111-115` 的注释就是讲这个），**碎片化才是真风险，所以 `expandable_segments:True` 必须保留**。真实数字以 smoke test 为准。 |
| **hash 表会不会因为 `log2_hashmap_size=24` 发生碰撞** | **[实测] 不会碰撞，因为它根本不是 hash。** 最细层分辨率 216 → (216+1)³ = 10,218,313 个格点 < 2²⁴ = 16,777,216，**每一层都低于上限**，所以是稠密网格。参数总数算得 **50,298,702**，与 `MIGRATION_5070.md:44` 记录的 F0 flexible INR 的 **50,298,960** 基本吻合（差 258，是 tcnn 取整规则的细节）。含义：`-hs/--log2_hashmap_size` 在当前设置下**完全不起作用**，除非降到 23 以下。 |
| **`apply_shift` / `n_shift` / `numpoints` / `dcf_norm` 与 notebook 是否一致** | **[源码] 一致。** trainer 用 `apply_shift=False` + `n_shift=(N/2+shift[1], N/2+shift[0])`，`numpoints` 默认 6，`--dcf_norm` 默认 `mean`；P2 notebook line 276-281 逐项相同。唯一不同的是 `support_mask`（trainer 传 mask，notebook 传 None 后另外乘），不构成失配。 |
