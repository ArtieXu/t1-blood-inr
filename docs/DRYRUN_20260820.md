执行：2026-08-20，在云端容器（**无 GPU**）
harness：`tools/dryrun/`（可复跑）

## 为什么做这个

我碰不到你的 5070，Gate A/B 必须你在 WSL 里跑。但**整条链路里只有 tcnn 一半真的需要 GPU**——argparse 校验、h5py 读取、DCF、SpiralNUFFT、scale 分位数、四项 loss、CSV/savemat/PNG 写出、run_info、逐帧残差表，这些全都能在 CPU 上跑。
先在这里把 bug 找出来，比在 5070 上烧时间发现要好。

## 怎么做的

跑的是**项目自己的 `train_inr_unsup_spiral.py`**，只做两处替换，且在启动时打印出来：

1. `tinycudann` → 一个**形状忠实**的 CPU 桩（`dryrun/stub/tinycudann.py`）：构造签名、`n_output_dims`、autograd 行为都一致，所以下游每一行代码看到的东西和在 GPU 上一模一样。**它不复现 hash 编码和 FullyFusedMLP 内核。**
2. `INR.build_pos` 里的 `device='cuda'` → CPU。

数据是合成的 `synth_gassp.mat`，键名、轴序、MATLAB v7.3 复数布局与真实文件完全一致，用**项目自己的 `load_spiral.py`** 读进来验证过：

```
kdata (10,4,800) complex128 · ktraj (10,2,800) · smap (4,64,64) · wi (10,800) · mask (64,64) · N=64
|ktraj|max = 3.1416 rad (pi = 3.1416)      wi 无负值
```

规模缩小到 10 帧 / 4 线圈 / 64² / 800 采样（真实是 50 / 28 / 216² / 3315）——逻辑完全相同，内存和时间可控。

### U1 的自定义 autograd 单独做了数学核验

`_PrecondForward` 声称「forward 用 A，backward 用 A^H W」。逐条验：


## 二、这次新发现的问题

### N1 · `model.py` 里有两处写死的 `cuda`，代码无法纯 CPU 运行 **[实测]**

- `model.py:80-83, 95-107` — `build_pos` / `build_ssr_pos` / `build_tsr_pos` 里 `torch.linspace(..., device='cuda')`
- `model.py:129` — `enc_mask = torch.zeros_like(enc).to('cuda')`（只在 `-m/--mask` 时走到）

`-m` 那条在我的干跑里直接报 `RuntimeError: Found no NVIDIA driver`。

**在 5070 上不影响任何东西**，但它意味着**这份代码完全不能纯 CPU 调试**——排查数据/算子问题时没法脱离 GPU。如果以后想留这条退路，把这两处改成 `device=<传入的 device>` 即可（我没有改，因为 `model.py` 在 manifest 里有 SHA-256）。

### N2 · 路径解析规则不一致，容易踩 **[实测]**

| 参数 | 相对路径基准 |
|---|---|
| `--data_path` | **脚本所在目录**（`train_inr_unsup_spiral.py:279`） |
| `--temporal_basis_path` | **脚本所在目录**（line 303-304） |
| `--shared_init_path` | `abspath(expanduser(...))`，即 **CWD** |
| 输出 `log_path` | **CWD**（line 411） |

我第一次跑 rank-5 就栽在这：在 `out/` 目录下传相对路径 `ir_rank5_10frames.npy`，脚本去项目根目录找，报 `FileNotFoundError`。
**建议一律传绝对路径**，`smoke.sh` 已经这么做了。

### N3、N4 · 我自己的 `check_run.py` 被这次测试查出两个缺陷（已修）

- **N3（较严重）**：旧版**无条件**豁免 `dc_holdout_*` 列的 nan 检查。如果开了 `--holdout_every` 但帧划分没生效、那几列全是 nan，旧版会**静默判 PASS**。现在只在 `holdout_every == 0` 时豁免，并额外打印 train/holdout 两个残差值。
- **N4**：趋势警告里写死了 "over 32 steps"，现在用实际步数。

修完重跑，holdout 那一档正确输出了 `holdout split active: train_uniform_rel=1.0075e+00  holdout_uniform_rel=1.0066e+00`。

同时给 `check_run.py` 加了两项：期望形状改为**从 `run_info.json` 的 `frames`/`grid_size` 推导**（不再写死 216），偏离真实 GASSP1 契约时单独告警；以及 `kb_grid_size` 为 `null` 或不等于 324 时告警。

## 三、这个测试**不能**证明什么

必须说清楚，否则容易被当成比它实际更强的证据：

1. **tcnn 是桩。** 关于 sm_120 内核、真实 hash 编码、FullyFusedMLP、以及 INR 那一半的真实显存，这个测试**一个字都没证明**。那只能靠你在 5070 上跑 `probes/tcnn.py`。
2. **数据是合成的、缩小的。** 10 帧 / 4 线圈 / 64² / 800 采样 vs 真实 50 / 28 / 216² / 3315。验的是**逻辑**，不是数值也不是性能。
3. **`--shared_init_path` 的「逐位相同」是用桩得出的**，而桩的初始化完全由 `torch.manual_seed` 控制——所以只固定 seed 的那一档也给出了同样的数字。**这一测只证明保存/加载/架构校验的管路是通的，完全没有回答「真 tcnn 是否需要 shared_init」这个问题。** Gate C 之前仍然要在 5070 上实测两次同 seed 的 run 是否逐位相同。
4. **合成数据是随机的**，所以 loss 的绝对值、下降幅度、`dc≈1.0` 这些数字没有任何科学含义。
